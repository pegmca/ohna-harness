# ohna Desktop 体验对齐测试用例

日期：2026-10-31  
范围：ohna-desktop（Electron）与 Codex、Claude、WorkBuddy 同类编码 Agent 的体验对齐  
目的：通过真实 UI 操作（computer use）发现体验问题，并作为回归用例。

## 统一前置条件

- `pnpm dev` 已启动，Electron 主窗口可见。
- `~/.ohna/settings.json` 已配置可用的真实 provider（Bridge AI）与 HTTP 代理。
- 已授权至少一个真实工作目录（仓库根）。
- 除注明外，不使用 mock；LLM 与工具调用均走真实链路。

## 验收记录约定

- **成功**：目标状态在真实窗口中可见，且与 runtime/磁盘记录一致。
- **失败**：记录具体可见错误、卡住的步骤、复现率与截图位置。
- **视觉/布局用例**：除真实窗口截图外，必须记录 `viewport`、关键元素 `getBoundingClientRect()`、
  页面 `scrollWidth/scrollHeight`、内部滚动容器及控制台错误。只写“看起来正常/拥挤”不算通过。
- **可判定信号**：文字密度、层级、对齐、遮挡、溢出、滚动归属、焦点状态均拆成可自动断言的
  数值或 DOM 契约；computer use 负责发现症状，Playwright 几何检查负责稳定回归。
- 每个用例结束后回到会话页，避免遗留运行状态影响后续用例。

## 视觉体验用例

### 视觉体验的统一验收方法

后续新增视觉/交互用例时，按下面四层写，避免只能依赖主观截图：

| 层 | 查什么 | 判定方式 |
| --- | --- | --- |
| 真实操作 | 入口能否打开、键盘/鼠标是否可操作 | computer use 截图 + AX 状态 |
| 几何 | 弹层/浮层是否完全在 viewport 内 | `getBoundingClientRect()` 四边与 `innerWidth/innerHeight` |
| 溢出 | 页面/区域是否出现意外横移 | 根节点与 body 的 `scrollWidth` 同 viewport 比较 |
| 滚动归属 | 长列表是否只让内部列表滚动 | 目标容器 `overflowY` + `scrollHeight > clientHeight`，滚动后页面 `scrollY` 不变 |

此外还要断言：

- 文字信息不得在同一层级重复（组标题、模型名、描述各自只承担一种信息）。
- 字号取设计 token；不得用 viewport width 缩放字号。
- 交互后焦点、选中态、禁用态仍有明确可访问名和可见反馈。
- 验收产物至少包含截图、几何 JSON、控制台错误；截图只能作为人工复核证据，
  不得代替数值断言。

实现建议：

1. 用 computer use 先发现“看起来不对”的症状并截取原状。
2. 把症状翻译成上面四层的可判定断言，先看测试 RED。
3. 只改造成 RED 的层级（结构 / CSS / 交互），再跑 GREEN。
4. 保留脚本和 metrics，后续同类页面复用同一检查器，避免只修单个选择器。

### UX-001 模型选择菜单的密度与视口边界

**对齐对象**：Codex / Claude 的紧凑模型菜单。

**步骤**
1. 打开 composer 模型选择器。
2. 在 `1440×900`、`1280×800`、`960×640` 视口分别检查菜单。
3. 滚动模型列表到底部，并切换一个模型。

**可判定预期**
- 每个模型项只显示一次模型名；组名只在组标题出现，不再拼进每项描述。
- 菜单四边均在视口内（允许 1px 亚像素误差），不产生页面横向滚动。
- 模型列表是独立滚动容器；滚动它不应带动页面或把菜单底边撑出视口。
- 菜单关闭后所选模型显示在 composer；控制台无错误。

**回归证据**
- 截图：`test/artifacts/ohna-model-menu/{width}x{height}.png`
- 几何：`test/artifacts/ohna-model-menu/metrics.json`
- 自动检查：`node test/verify-ohna-model-menu.mjs`

**2026-10-31 回归结果**

- 初始复现：模型菜单约 320px 宽却从底栏顶到视口顶部，19 个模型每项重复“组名 · 模型 id”。
- 修复后：模型项只保留模型名，组名只在组标题出现；选中项只显示勾选；列表最大高度
  `min(420px, calc(100vh - 180px))` 并独立纵向滚动。
- 三视口（1440×900 / 1280×800 / 960×640）几何检查全部通过；菜单四边在视口内，
  `pageScrollWidth === viewport.width`，滚动列表后页面 `scrollY` 保持 0。

## 用例

### UC-001 首次启动与工作区可见性

**对齐对象**：Codex / Claude / WorkBuddy 的工作区定位。  
**前置条件**：启动新进程，不存在旧窗口。

**步骤**
1. 启动桌面应用。
2. 检查默认窗口大小、左栏与 composer 上方的信息。
3. 打开工作区选择器。

**预期**
- 窗口默认至少 1440×900，主工作区一眼可见，无横向滚动条。
- composer 上方显示当前目录名、Git 分支、完整路径。
- 工作区选择器可打开，已有授权目录可选。

**失败信号**：窗口过小、路径被裁切、工作区信息缺失。

### UC-002 从侧栏添加工作目录

**对齐对象**：多项目工作流的入口一致性。  
**前置条件**：当前只有一个已授权工作区。

**步骤**
1. 点击左侧“添加工作目录”。
2. 在原生目录对话框中选择另一目录。
3. 检查工作区选择器与会话分组。

**预期**
- 新目录授权成功，并被选中为当前工作区。
- 会话列表出现新工作区分组，旧会话保持原归属。
- 新建会话绑定到新目录。

**失败信号**：入口不存在、授权后无变化、错误绑定到默认目录。

### UC-003 同组多模型选择与真实生效

**对齐对象**：Codex 式分组模型选择。  
**前置条件**：settings 中已有多个模型分组。

**步骤**
1. 打开 composer 的模型选择器。
2. 记录组名与模型数量。
3. 切换到非默认模型（如 `deepseek-v4-pro`）。
4. 发送一条短消息。

**预期**
- 模型按组展示，组内多模型，不存在全量平铺。
- composer 显示选中的模型。
- run 元数据与真实 LLM 请求中的 modelId 均为所选模型。

**失败信号**：只有单模型、切换后 modelId 仍为默认值。

### UC-004 新会话创建与消息完整链路

**对齐对象**：主流 Chat 的基础稳定性。  
**前置条件**：工作区与模型均可用。

**步骤**
1. 点击 New Chat。
2. 输入并发送一条消息。
3. 等待回答完成。

**预期**
- 新会话标题正确生成并进入侧栏。
- 用户消息只出现一次。
- 助手从 running 自动转为 completed，出现真实回答，无空白完成。

**失败信号**：会话被静默创建在错误工作区、重复消息、永久 running。

### UC-005 模型调用失败的可诊断性

**对齐对象**：Claude/Codex 的错误透明度。  
**前置条件**：provider 不可达或 API key 无效（可临时切换配置）。

**步骤**
1. 发送一条消息。
2. 等待请求结束。
3. 查看 run 状态与错误内容。

**预期**
- run 明确为 failed，而不是 completed。
- 显示真实 provider 错误（网络失败、401、超时等）。
- 不产生伪造的“已完成”空回答。

**失败信号**：错误被吞、状态为 completed、无错误信息。

### UC-006 会话历史与运行状态恢复

**对齐对象**：跨会话/刷新后的工作连续性。  
**前置条件**：已有完成的会话与至少一个 run。

**步骤**
1. 打开历史会话。
2. 切换至 Trace 面板。
3. 检查 run 状态与事件记录。

**预期**
- 历史消息按原顺序展示。
- Trace 中 run 为真实终态（completed/failed/cancelled）。
- 刷新后不会出现 running 残留。

**失败信号**：历史事件丢失、状态永远 running。

### UC-007 侧栏长工作区名与标题的可用性

**对齐对象**：密集工作区列表的可读性。  
**前置条件**：存在长 workspaceId 与长会话标题。

**步骤**
1. 缩小或恢复正常窗口宽度。
2. 检查组名、会话标题、归档按钮。
3. 滚动会话列表。

**预期**
- 无横向滚动条，无文字被硬截断。
- 超长内容用省略号展示，按钮完整可点。
- 纵向滚动正常。

**失败信号**：文字越过边界、按钮不可见、出现横向滚动条。

### UC-008 设置中的 provider 与代理配置

**对齐对象**：可配置的企业/代理环境。  
**前置条件**：settings 中已有一个 provider。

**步骤**
1. 打开设置 → 模型。
2. 修改 provider baseUrl、API key、HTTP 代理。
3. 点击保存。

**预期**
- 设置页显示当前真实配置。
- 保存后写入 `~/.ohna/settings.json`，权限为 0600。
- 保存不走 HTTP，不污染仓库配置。

**失败信号**：设置只读、配置写回 `.env`、密钥进入仓库。

### UC-009 分组模型拉取与编辑

**对齐对象**：多模型目录的可维护性。  
**前置条件**：provider 的 `/v1/models` 可访问。

**步骤**
1. 在设置页点击“从 /v1/models 拉取模型”。
2. 查看拉取结果与分组。
3. 编辑组名并将某个模型设为默认。
4. 保存配置。

**预期**
- 拉取到真实模型列表并合入分组。
- 组名可编辑，默认模型可切换。
- 保存后 composer 与 run 使用新默认模型。

**失败信号**：拉取无结果、分组丢失、默认模型不生效。

### UC-010 工具调用与权限确认的可控性

**对齐对象**：编码 Agent 的操作安全性与可控性。  
**前置条件**：真实模型可产生工具调用。

**步骤**
1. 发送一条要求读取文件的指令。
2. 观察工具调用与状态。
3. 如出现确认卡片，分别测试允许与拒绝。

**预期**
- 工具调用状态可见（pending / completed / error）。
- 确认卡片可提交决定，工具只执行被允许的操作。
- run 不会因权限确认而永久卡住。

**失败信号**：工具状态不明、权限决定无响应、run 悬挂。

## 回归优先级

- **P0**：UC-003、UC-004、UC-005、UC-006（模型选择、消息完成、错误可见、状态恢复）。
- **P1**：UC-001、UC-002、UC-007、UC-008、UC-009（工作区与配置可用性）。
- **P2**：UC-010（工具权限与细粒度控制）。
